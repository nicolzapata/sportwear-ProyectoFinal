Manual técnico de implantación de SportWear

Guía completa para clonar, configurar, ejecutar en local y desplegar en producción el sistema de gestión y venta de SportWear: catálogo público, carrito, checkout y panel administrativo.

02

Requisitos

Lo que necesitas instalado o creado antes de tocar el código.

  • Sistema operativo: cualquiera con soporte para Node.js 18+ (Windows, macOS o Linux). El backend se conteneriza sobre node:18-alpine para producción.
  • Node.js 18 o superior, con npm.
  • Gestor de paquetes: npm.
  • Base de datos: PostgreSQL (instancia local o gestionada en la nube).
  • Cuenta de Cloudinary para el almacenamiento de imágenes de productos.
  • Cuenta de correo con acceso SMTP, usada para el envío de correos de recuperación de contraseña.

04

Clonación del proyecto

El repositorio es un monorepo con dos aplicaciones independientes: sportwear-backend/ (API) y sportwear/ (frontend). Cada una se instala y ejecuta por separado.

git clone https://github.com/nicolzapata/sportwear-ProyectoFinal.git
cd sportwear-ProyectoFinal

No hay pasos adicionales antes de instalar: la estructura de carpetas ya viene lista para entrar a cada aplicación.

05

Instalación de dependencias

Backend
cd sportwear-backend
npm install
Frontend
cd sportwear
npm install

No hay dependencias nativas ni pasos especiales: basta con Node 18+ y npm en ambos casos.

07

Configuración de la base de datos

Motor: PostgreSQL, mediante el driver pg.

  1. Crear la base de datos. Una instancia PostgreSQL vacía, local o gestionada, con el nombre que uses en DB_NAME (o dentro de la cadena DATABASE_URL).
  2. Configurar la conexión. En desarrollo se arma con DB_HOST, DB_PORT, DB_USER, DB_PASSWORD y DB_NAME. Si existe DATABASE_URL, esta tiene prioridad y se usa en su lugar (así funciona en Render), con SSL forzado — requerido por los proveedores de PostgreSQL gestionado.
  3. Ejecutar las migraciones incrementales. Los scripts SQL viven en sportwear-backend/sql/: agregar_cuotas.sql, agregar_fecha_vencimiento.sql, agregar_permiso_cuotas.sql, agregar_tipo_pago.sql, dedupe_y_completar_barrios.sql y eliminar_tipo_cliente_permiso_pagos.sql. Se ejecutan contra la base ya creada.
  4. Sincronizar módulos y permisos. Desde la raíz del monorepo: node fix-and-seed.js. Sincroniza los módulos del sistema (Dashboard, Usuarios, Roles, Productos, Colores, Catálogo, Proveedores, Compras, Pedidos, Ventas, Pagos) con sus acciones ver / crear / editar / eliminar.
  5. Verificar la estructura (opcional). Los scripts check-db.js, check-tables.js, check-schema.js, check-fk.js y check-constraint.js, en la raíz del monorepo, confirman que la base quedó en el estado esperado.
08

Ejecución local del proyecto

  1. Configuración previa. Repositorio clonado, dependencias instaladas y ambos .env configurados (secciones 4 a 6).
  2. Base de datos arriba. PostgreSQL corriendo localmente y con el esquema listo (sección 7).
  3. Ejecutar el backend. cd sportwear-backend && npm run dev. Arranca con nodemon e imprime ✅ Conectado a PostgreSQL en consola cuando la conexión es correcta. Queda disponible en http://localhost:4000 (o el PORT definido).
  4. Ejecutar el frontend. En otra terminal: cd sportwear && npm run dev. Vite lo sirve en http://localhost:5173.
  5. Direcciones de acceso local. Frontend en http://localhost:5173, API en http://localhost:4000/api.
  6. Verificación. Con ambos servicios activos, abre el frontend, inicia sesión y confirma en la consola del backend o en la pestaña Network del navegador que las peticiones a la API responden correctamente.

11

Configuración de producción

  • URLs: frontend en sportwearr.vercel.app, API en sportwear-proyectofinal.onrender.com/api.
  • Variables de entorno: cada plataforma mantiene su propio set — Vercel solo necesita VITE_API_URL; Render necesita el set completo del backend.
  • CORS: el backend restringe el origen con FRONTEND_URL. Ese valor debe coincidir exactamente con el dominio de Vercel (con https://, sin barra final) o el navegador bloquea las peticiones.
  • Conexión frontend–backend: exclusivamente a través de la URL pública de Render, nunca localhost.
  • Base de datos: conexión gestionada vía DATABASE_URL con SSL habilitado.
  • HTTPS: provisto automáticamente por Vercel y Render; no requiere configuración manual.
12

Solución de problemas frecuentes

Build de Vercel falla por sensibilidad a mayúsculas y minúsculas

Causa
El proyecto funcionaba en local (Windows/macOS no distinguen mayúsculas en las rutas de archivo), pero el build de Vercel corre sobre Linux, que sí las distingue. Un import no coincidía exactamente con el nombre real del archivo.
Solución
Corregir cada import para que coincida carácter por carácter con el nombre real del archivo en el sistema de archivos.

Rutas internas devuelven 404 al recargar la página en producción

Causa
React Router maneja el enrutamiento en el navegador, pero Vercel no sabe que debe servir index.html para rutas que no corresponden a un archivo real del build.
Solución
Agregar un vercel.json con una regla de rewrite que redirige todas las rutas hacia /index.html, dejando que React Router resuelva la navegación del lado del cliente.
